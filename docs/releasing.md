# 发布标准

源码更新、发布候选、GitHub Release 是三个不同阶段。默认提交源码；发布需要维护者明确决定。

## 什么时候值得发布

- 一个完整、可使用的新功能已经验收。
- 会影响正常使用的重要问题已修复，例如漏提醒、任务丢失、连接失败或异常 CPU 占用。
- 积累了一组经过验证的小改进，值得让用户集中升级一次。

文案、命名、演示动画、小幅样式调整和单独的内部重构通常随下一批发布。紧急问题可单独发布修复版，但仍需相关验证和明确发布指令。不固定每天发布，也不按提交次数发布。

## 发布前必须具备

1. 说明本次解决的用户问题、兼容性影响及已知限制。
2. 相关回归测试、类型检查、支持平台的生产构建通过；不能只凭进程存活或测试数量宣布功能正常。
3. 涉及截图、保存、连接或提醒的改动，验证对应真实链路。完成提示必须对应真实结束事件；声音没有实测就写明未验证。
4. 核对当前绑定、用户配置和历史数据不会被升级误改；提供旧版回退路径。
5. 形成候选包后确认版本号、变更说明和发布范围。安装流程、其他机器或其他平台未验证时，明确标为候选版及具体限制。
6. 维护者明确要求发布后，才创建标签、上传并公开 GitHub Release。未满足条件时源码可以继续推进，安装包留作本地验证。

## 工作流

`Release` 工作流只允许手动触发，需选择与 package.json 版本匹配的现有 `v<版本>` 标签。工作流只准备草稿及构建资产，不自动公开。提交代码或推送标签不会触发 Release，也不覆盖已公开的同名发行版。

本地生产构建同样不自动发布。README 的下载地址只在对应 Release 已实际发布时更新，不能提前指向不存在的下载包。当前支持平台是 Windows；macOS 实验性构建不能当作 Windows 发布验收的替代。
